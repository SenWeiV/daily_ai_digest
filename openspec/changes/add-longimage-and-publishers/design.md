## Context

`EmailService.send_digest_email()` in `backend/app/services/email_service.py` builds a `MIMEMultipart("alternative")` holding a plain-text part and an HTML part, and hands it to SMTP. `_generate_html_template()` builds that HTML inline — GitHub, arXiv, and YouTube sections with inline CSS and emoji. `digest_service.generate_digest()` orchestrates collect → select → analyze → save → send, so anything new hooks in between save and send, where the items are final and analyzed.

Four facts about the current code determine the shape of this change:

- The multipart subtype is `alternative`, which means "these parts are the same content in different formats; show one." Adding an image to it makes the image an *alternative to the body*, and clients legitimately choose to show it instead. Attachments require a `mixed` container.
- `Dockerfile.backend` is `python:3.11-slim` with only `gcc` and `libsqlite3-dev`. No browser, no fonts. Rendering Chinese text in this image today would produce tofu boxes for every character, and there would be no browser to produce them with.
- `_generate_html_template()` has two `<span>??</span>` spots at lines 196 and 210 — existing mojibake. Rendering the HTML to an image makes latent encoding problems visible rather than easy to overlook.
- Every existing LLM call site is text-only. `analyze_github_repo` takes README text, `analyze_arxiv_paper` takes only the abstract (the PDF is never fetched), `analyze_youtube_video` takes the transcript fetched by `youtube_transcript_api`, and `generate_period_summary` takes already-written summaries. The only image anywhere is `thumbnail_url` at `youtube_agent.py:373`, which is stored as a link and never sent to a model. So no *analysis* step needs vision.

That last point is why the model split falls out the way it does. Vision is needed for exactly one thing in this pipeline: looking at an image the pipeline itself just produced and judging whether it came out right.

**On the connectivity question:** the mainland-China host cannot reach `api.twitter.com`, `graph.facebook.com`, or `oauth.reddit.com` without a VPN. 微信公众号 and 知乎 are reachable, but 微信公众号 individual subscription accounts lost `freepublish` in 2025-07 so the ceiling is a draft, and 小红书 has no official publish API and actively restricts automated posting. After removing the unreachable three and the one that bans automation, two remain and one can only produce a draft. That is what makes delivery-only the right design rather than a compromise.

**Verified provider facts as of 2026-08-01.** Kimi K3 is GA, model id `kimi-k3`, 1M context, natively multimodal over both image and video via MoonViT-V2. Image input must be a base64 data URL or a Files-API reference (`ms://<file-id>`); public HTTP image URLs are explicitly not supported, and `content` must be a real JSON parts array. Body limit 100 MB, no cap on images per request, practical resolution sweet spot around 3584×3584. Pricing is ¥2 / ¥20 / ¥100 per M tokens for cache-hit input / cache-miss input / output, and `reasoning_effort` defaults to `max` with no way to disable reasoning, so output cost is structurally high. Two endpoints exist and are separate platforms with separate accounts and currencies: `api.moonshot.cn` measured 10/10 reachable at ~0.1s from a Beijing IP, `api.moonshot.ai` only 6/10 with four timeouts. On text-in-image ability, the strongest published number is OmniDocBench 91.1, the best of the five models compared, and OmniDocBench's page set is deliberately balanced across Chinese and English. There are no OCRBench, DocVQA, ChartQA, or CCBench numbers for K3 — the full tech report was searched and none exist — and no independent third-party vision evaluation. All vision numbers are vendor-reported.

Doubao Seed was evaluated as the alternative for the inspection role. Current vision model is `doubao-seed-2-1-pro-260628` on `https://ark.cn-beijing.volces.com/api/v3`, OpenAI-SDK compatible, accepting both base64 data URLs and public URLs, 256k context, ¥6 / ¥30 per M tokens in / out with images billed at the plain text input rate and `detail: "high"` costing a flat 1280 tokens per image. Body limit 64 MB, 10 MB per base64 image. Reachability confirmed at 69 ms from a mainland IP with no VPN. Published vision numbers are OCRBench v2 63.2, ChartQA Pro 70.9, MathVista 90.7, MMMU-Pro 81.6 — the OCRBench v2 figure beats both GPT-5.5 (61.1) and Gemini-3.1 Pro (62.8). Note that Seed 2.1 publishes only the v2 and Pro variants; classic OCRBench, DocVQA, and ChartQA figures exist only for the older Seed1.5-VL (DocVQA 96.9, OCRBench 861, MMBench-cn 89.1 at near-parity with MMBench-en) and that model could not be mapped to any current Ark model id, so those numbers must not be attributed to 2.1. Video on Ark is **frame-sampled, not native** — the docs describe FPS-based keyframe extraction with injected `[<n> second]` text markers, 0.2–5 fps, capped at 81,920 tokens per video — which is irrelevant here since no step needs video, but it contradicts the assumption that Ark offers native temporal modelling.

Seedream image generation is available on the same Ark host at `POST /api/v3/images/generations` with plain `Authorization: Bearer` auth, synchronous, returning the image URL in the same response. Four callable models: `doubao-seedream-5-0-pro-260628`, `doubao-seedream-5-0-260128` (alias `doubao-seedream-5-0-lite-260128`), `doubao-seedream-4-5-251128`, `doubao-seedream-4-0-250828`. Three facts about them decide the design below. **5.0 pro cannot do 组图** — consistent multi-image series — while lite, 4.5, and 4.0 can, via `sequential_image_generation: "auto"`. **5.0 lite enforces a minimum total-pixel floor of 3,686,400** and a ceiling of 16,777,216. **`watermark` defaults to `true`**, stamping "AI生成" bottom-right, and generated image URLs **expire after 24 hours**. Pricing is ¥0.22 per output image flat for lite, with input reference images free. On Chinese text rendering the only quantitative figure published anywhere is from the Seedream 3.0 paper — a 94% text availability rate for Chinese and English — and no equivalent metric exists for 4.x or 5.0; Ark's own 5.0 docs contain zero text-rendering metric, and ByteDance's launch post concedes "room to improve in finer-grained text rendering." An independent single-tester field test of dense Chinese infographics found ten distinct errors at full resolution, clustered in caption-size text while large headings stayed correct. That evidence is unaudited but it agrees with the vendor's own admission, and it is the direct justification for keeping accurate text out of generated pixels entirely.

One operational fact forces action regardless of preference: `kimi-k2.5`, which is what production runs today, **sunsets 2026-08-31**, along with the entire `moonshot-v1-*` series. The text model has to move this month either way.

## Goals / Non-Goals

**Goals:**

- Remove the manual production work: the ultra-HD long image, five platform-styled images, and six platforms' copy arrive in one email.
- Never deliver a broken image. Missing glyphs, clipped text, and overflow are caught by an automated gate before anything leaves.
- Keep the operator as the publish decision-maker. No credentials, no tokens, nothing to be rate-limited or banned.
- Keep text analysis cheap by keeping it on a text model, and pay for vision only where vision is the thing being used.
- Render Chinese and emoji correctly, which means the container image has to change and font resolvability has to be checked at startup.

**Non-Goals:**

- No publishing API calls, no OAuth, no credential storage, no scheduled posting.
- No VPN or proxy configuration on the server.
- No change to discovery, selection, grading, or to which items appear in a digest.
- No use of vision for content analysis. arXiv figures, YouTube frames, and repository screenshots stay out of scope; the analysis inputs are unchanged.
- No web UI for previewing or approving images before send. The gate is automated; the email is the interface.
- No speed optimization at the expense of correctness. Slower runs are explicitly accepted.

## Decisions

**Delivery-only, no publishing integration.** Detailed in Context. The decisive point is not that automation is hard but that it is nearly pointless here: after removing the three unreachable platforms and the one that bans automation, two remain and one can only produce a draft the operator still has to open and publish. Alternative considered: automate 微信公众号 drafts plus 知乎. Rejected for now — it adds credential handling and token refresh for a benefit the operator barely feels, since they are already opening the email.

**Two model roles, not one multimodal model for everything.** Text analysis and copy generation run on DeepSeek V4 Flash; visual inspection runs on `kimi-k3`. The reason is a cost asymmetry that follows directly from call counts. Text analysis runs 10–24 times per digest and needs no vision. Inspection runs roughly 6–8 times per digest and needs nothing but vision. K3 output is ¥100/M with reasoning permanently on; DeepSeek V4 Flash output is $0.28/M. Putting the 24 text calls on K3 would pay a two-orders-of-magnitude premium for a capability those calls cannot use. Alternative considered: one model for both, for operational simplicity. Rejected on that arithmetic — the simplicity is real but it is bought with a recurring daily cost for nothing. Alternative also considered: skip vision entirely and keep human visual checks. Rejected because the user's requirement is that tofu boxes must never ship, and a human check that happens after the email has been sent cannot enforce that.

**K3 for inspection, with Doubao Seed 2.1 Pro as the documented alternative.** The two are close enough that this is a judgement call rather than a clear win, and it is worth recording why it went the way it did. K3's relevant number is OmniDocBench 91.1 — document parsing, best of five models compared, on a page set balanced across Chinese and English. Seed 2.1 Pro's is OCRBench v2 63.2, which beats GPT-5.5 and Gemini-3.1 Pro on that benchmark. Neither publishes a number for the actual task here, which is "look at this rendered card and tell me whether any glyph failed to render." The benchmarks are proxies.

What tips it to K3 is price shape under retry. Seed 2.1 Pro bills images at the text input rate with `detail: "high"` costing a flat 1280 tokens per image, so its input cost per inspection is trivially small — but its output is ¥30/M against K3's ¥100/M, and inspection output is a short structured verdict either way, so the absolute difference per call is small in both directions. The deciding factor is that K3's 1M context and 100 MB body limit let a tall segment be inspected in one request, where Seed's 256k context and 64 MB body limit with 10 MB per base64 image would force more aggressive segmentation of the long image — and more segments means more calls, which is the axis that actually drives cost here.

Seed 2.1 Pro remains the better choice on two counts worth writing down in case this is revisited: it accepts public image URLs as well as base64, which K3 does not, and it is on the same host and credential as Seedream, so choosing it would collapse three provider accounts into two. If the K3 inspection cost proves higher than modelled, switching is a configuration change, not a redesign — which is the whole point of making the roles independently configurable. One thing that must not enter the comparison: Ark video is frame-sampled with injected timestamp markers rather than natively modelled, so any impression that Seed offers native video understanding is wrong. It is irrelevant here because nothing in this pipeline sends video, but it would be a false premise if the roles were ever reconsidered for a video feature.

**Seedream 5.0 Lite for generation, not 5.0 Pro, and the reason is 组图.** The multi-page 小红书 set is the case that matters, and **5.0 Pro cannot generate a consistent series** — that capability exists on lite, 4.5, and 4.0 via `sequential_image_generation: "auto"`, and is absent on Pro, which instead offers interactive region editing that this pipeline has no use for. Four independently generated backgrounds look like four unrelated posts, which defeats the purpose of a set. So the higher-tier model is disqualified by the one feature the use case depends on. Lite is also cheaper at ¥0.22 flat per output image against Pro's ¥0.30–0.60, so nothing is being traded away.

**Generation resolution is dictated by Lite's pixel floor, not by the frame size.** 5.0 Lite enforces a minimum total-pixel count of 3,686,400. Every target frame is below it: `xhs-cover` at 1242×1656 is 2.06M pixels, `x-card` at 1600×900 is 1.44M, `ig-square` at 1080×1080 is 1.17M. So Lite cannot be asked for the frame's logical size at all — the request would be rejected. It must be asked for a 2K-or-higher tier and the result downscaled locally to the frame. This is fortunate rather than awkward: the frames are composited at 2× DPR anyway, so `xhs-cover` needs 2484×3312 = 8.23M pixels, which is above Lite's floor and within its 16.7M ceiling. Generating at 2K–3K and downscaling to the composite size is both required by the provider and correct for output quality. What the spec forbids is the opposite move — generating small and upscaling — because the resulting softness is indistinguishable from a rendering defect and would either fail inspection or ship a soft image.

**Watermarking is a configuration setting that defaults to off, and generated URLs must be downloaded immediately.** Two provider defaults that would produce wrong output if left alone. `watermark` defaults to `true` on Ark and stamps "AI生成" into the bottom-right corner, which would appear in delivered images without the operator having chosen it. Rather than hardcoding `false` at the call site, watermarking is its own setting whose default is disabled, and its value is sent explicitly on every request — that way the field is never absent (absence means watermarked), and an operator who does want provenance marking can turn it on without editing code. And generated image URLs expire after 24 hours, so storing the URL as the asset reference means the digest record points at nothing by the next day. Both are the kind of default that is only discovered by shipping the bug, so they are requirements rather than notes.

**No cross-role fallback, in either direction.** A text-only model cannot inspect an image, and sending one an image part yields either an error or a confidently fabricated verdict — the second being far worse, since a fabricated pass ships a broken image. So when the vision model is unavailable, images are not marked as passing and the email goes out without them. The spec states this explicitly because "fall back to the other model" is the reflex here and it produces exactly the failure the gate exists to prevent.

**`api.moonshot.cn`, not `api.moonshot.ai`.** Measured from a Beijing IP: 10/10 versus 6/10 with four timeouts. The two are separate platforms with separate accounts, credentials, and currencies, and neither one's documentation acknowledges the other exists. That undocumented split is a trap for whoever next edits the server `.env`, so the environment template has to say it in a comment rather than leaving it to be rediscovered.

**The QA gate is a hard gate, and a failing image is withheld rather than degraded.** Every other optional part of this change degrades to a lesser version of itself. Images do not: there is no acceptable lesser version of an image with a tofu box in it, because its only purpose is to be posted publicly. So the cycle is render → inspect → correct → re-inspect, bounded by a maximum attempt count, and an image that still fails is dropped from the email and named as dropped. The email still sends. The user's instruction was that broken images must never appear and that slower is acceptable; withholding is the only outcome consistent with both.

**Each retry must change something specific.** A retry that re-renders identical input produces an identical defect and burns a vision call. So the verdict carries a defect category, and the category selects the correction: font coverage failure applies a fallback font, overflow or clipping applies tighter truncation or a smaller type scale. The spec forbids a retry that differs in nothing from the failed attempt, which is the bug this rule exists to prevent.

**An unparseable verdict is a failure, never a pass.** The default on ambiguity has to be the safe direction. A model returning malformed output is the case where a permissive default would silently ship exactly the defect being checked for.

**Font checking happens at startup too, not only in the gate.** A missing CJK font makes every image fail every attempt, exhausting the retry budget across every image to discover one fact that a startup check establishes in one step. So the renderer verifies font resolvability at initialization, logs the resolved family names, and refuses to render if a required font is absent. The gate stays as the backstop for per-character coverage gaps that a family-level check cannot see.

**Inspection downscaling has a floor, and the floor matters more than the ceiling.** A 2× DPR long image can exceed the 100 MB body limit, so the inspection copy may be downscaled. But downscaling far enough makes text undetectable, and an inspection that cannot read the text will report a pass — a false pass being the single worst outcome in this design. So there is a minimum inspection resolution, and an image too large to inspect above that floor is inspected in segments instead. The delivered image always keeps full resolution; only the inspection copy is ever reduced.

**Images are submitted as base64 or file reference.** Not a design choice: K3 does not accept public HTTP image URLs, and `content` must be a genuine parts array rather than a serialized string. Since the images are rendered locally and already have to be read from disk, base64 is the natural path. Files API is worth it only if the same image is inspected repeatedly.

**Generated imagery is background only, and never carries text that must be correct.** Any project name, figure, or link in an image is composed by the template layer over the generated background. The reason is verifiability: template text is the digest's own string and can be checked mechanically, whereas text a generation model draws into pixels can only be checked by reading it back with another model — a loop that costs more and still cannot guarantee the string matches. The evidence supports the constraint rather than merely motivating it: the only published quantitative figure for Chinese text rendering in Seedream is 94% availability, from the 3.0 paper, with no equivalent metric for 4.x or 5.0; ByteDance's own 5.0 launch post concedes room to improve in finer-grained text rendering; and an independent dense-infographic test found ten distinct errors at full resolution, with failures clustered in caption-size text while large headings stayed correct. A 94% per-character availability rate is unacceptable for a project name — a single wrong glyph in a repository name makes the post wrong. So generation does what it is reliable at, which is looking good, and the facts stay in the layer that can be proven right. A non-generated fallback background is required so a generation failure degrades to a plain designed image rather than to no image.

**Generation prompts must reserve quiet regions for composited text.** A background with high-contrast detail exactly where the title lands produces an image that fails the legibility check even though both layers are individually fine. Requesting low visual complexity in the text regions is cheaper than discovering the collision through the QA gate and burning a retry on it.

**Style is declared as inspectable data, not buried in prompt strings.** The per-platform style — tone, structure, palette, type scale, density — lives as structured data that both the copy prompt and the image prompt read. Otherwise the 小红书 look exists only inside a prompt literal, and changing it means editing prose and hoping. Alternative considered: hand-write one prompt per platform and reuse it unchanged. Rejected because the prompt has to reflect the day's actual content to be useful, so it has to be constructed per run anyway.

**A multi-page set shares one visual treatment via shared template plus shared conditioning.** Four 小红书 pages generated independently look like four unrelated posts. Shared palette and type scale come from the template; where generated backgrounds are used across a set, a shared conditioning input or seed keeps them from diverging.

**One email, and the send waits.** The user asked for this directly. It also falls out of the gate: the set of attachable images is not known until every image has passed or been withheld, so there is nothing to send early. Alternative considered: send the digest immediately and the assets in a follow-up. Rejected — it is what the user explicitly ruled out, and it would also mean the digest email cannot reference its own attachments.

**Chromium in the image, and its size is the real cost.** `fonts-noto-cjk` for Simplified Chinese and `fonts-noto-color-emoji` specifically because it is CBDT bitmap, which Chromium renders, unlike SVG-based emoji fonts. `--disable-dev-shm-usage` is mandatory: the container's default `/dev/shm` is 64 MB, Chromium exceeds it, and the symptom is an opaque crash rather than an out-of-memory message. The image grows by several hundred megabytes, which the tasks measure rather than estimate.

**Everything is disable-able and every step fails independently.** Rendering, generation, and inspection each have their own switch, and each failure domain is isolated. The concrete scenario being defended against: Chromium crashes on the server for an unrelated reason and the daily email stops arriving. Rendering ships defaulted off so landing this change cannot break the daily email before the render path is proven inside the container.

## Risks / Trade-offs

- **The vision model reports a false pass and a broken image ships** → This is the failure the whole gate exists to prevent, and it cannot be fully eliminated: K3's vision numbers are all vendor-reported, there is no independent third-party evaluation, and there are no published Chinese-OCR-specific scores. The mitigations are the inspection-resolution floor, treating unparseable verdicts as failures, and the startup font check that removes the most likely defect class before inspection is relied on. Residual risk is real and worth stating plainly rather than implying the gate is airtight.
- **Retry loops make runs much slower** → Accepted explicitly; the user chose correctness over speed. Bounded by the maximum attempt count so it cannot run unbounded.
- **Retries multiply vision cost on a bad day** → A systematic defect makes every image fail every attempt, multiplying the cost. The startup font check removes the most likely systematic cause, and per-role call logging makes the cost visible after one bad run rather than after a billing surprise.
- **Generation retries multiply per-image spend** → Generation is billed per output image, not per token, so a QA retry loop that regenerates backgrounds each time spends real money per attempt. Bounded by a configured per-run cap on generated images, above which retries fall back to the plain background. The cap matters more than the retry limit here because the two multiply.
- **Seedream's Chinese text rendering is weak at caption size and the only hard number is from 3.0** → Not a risk this design takes on, because generation never renders text that must be correct. Recorded because it is the reason for that constraint, and because relaxing the constraint later would import the risk wholesale.
- **The inspection model choice is a judgement call on proxy benchmarks** → Neither K3 nor Seed 2.1 Pro publishes a number for "detect a missing glyph in a rendered card." OmniDocBench 91.1 and OCRBench v2 63.2 are proxies for it. Switching is a configuration change, which is the reason the roles are independently configurable rather than hardcoded.
- **Three provider accounts instead of one** → DeepSeek, Moonshot mainland, and Volcano Engine Ark, each with its own credential and billing. Choosing Seed 2.1 Pro for inspection would collapse it to two, since Ark hosts both Seed and Seedream. Accepted for now; noted so the consolidation option stays visible.
- **Image size makes the build slow and the disk tight** → Measured before rollout. If unacceptable, the fallback is a separate renderer container, which is more moving parts but keeps the backend image small. Not doing that now because one container is simpler and the size may well be fine.
- **Chromium works locally on darwin and fails in the linux container** → The only meaningful verification is inside the built container. Local success proves nothing about the deployment.
- **Generated copy is fluent and confidently wrong** → Grounding requirement plus mechanical URL and figure checks. This cannot catch everything, and the residual risk is real: the operator is still the last check before anything is posted. The email presents copy as a draft to review.
- **Chinese character counting for X differs from what the platform counts** → X counts CJK as two toward its 280 limit. Getting this wrong produces copy that passes validation and is rejected at post time.
- **`kimi-k2.5` sunsets 2026-08-31 and production runs it today** → Not a risk of this change but a deadline on it. The DeepSeek switch is what resolves it; noted here so the two changes are sequenced correctly.
- **Fixing the two existing `<span>??</span>` mojibake spots changes email output** → Small, visible, and an improvement. Called out so it is not mistaken for an unrelated regression.

## Migration Plan

1. Land the DeepSeek text-model switch first. It is a prerequisite for the role split and it has its own August deadline.
2. Land the renderer, publishers, QA gate, and email packaging behind configuration that defaults rendering off, so a deploy cannot break the daily email before the render path is proven in the container.
3. Build the image locally, measure the size increase against the current image, and record both.
4. Verify inside the built container that fonts resolve, that the startup check logs the resolved families, and that a Chinese-plus-emoji test page renders with no tofu.
5. Render a real stored digest inside the container. Verify the stitched height matches page height for a digest tall enough to require segmentation.
6. Run the QA gate against deliberately broken inputs — a font removed, a title long enough to overflow — and confirm each is detected, corrected, and passes on retry. A gate that has never caught a real defect has not been tested.
7. Generate copy for all six platforms and check every URL and figure against the digest.
8. Send one test email to the operator with attachments and the copy section. Confirm the HTML body renders as the body and the attachments appear as attachments in the actual mail client. Record total attachment size against the provider's limit.
9. On the server: record the current image tag, back up `/opt/daily_ai_digest/data/digest.db`, deploy with rendering disabled, confirm the daily email is unaffected.
10. Enable rendering and inspection, restart, and watch the first scheduled run. Record per-role call counts, retry counts, and wall-clock duration. If rendering fails, disable it in configuration and restart — the email keeps working and the failure stays diagnosable from logs.

## Open Questions

- Does the operator's mail provider impose an attachment limit below the seven images' total at 2× DPR? Determines the budget default. Measured in step 8, not blocking.
- What is the right maximum attempt count? Starting at three, to be revised once real retry rates are observed. Too low withholds recoverable images; too high multiplies vision cost on a systematically broken day.
- Is there a free image-generation quota on a new Ark account? The billing docs describe free quota only for token-billed online inference, and Seedream is billed per image, so no figure appears in any published doc. Visible in the console after signup; affects the first month's cost estimate only.
- Does Seedream 5.0 Lite's 3K tier or its 2K tier give the better composited result after downscaling to the frame? Both clear the pixel floor. Decided by looking at output, not by reasoning.
- Should the three 小红书 content pages be a fixed count or scale with item count up to a cap? Fixed at three for now; revisit once real digests at 20-plus items have been rendered.
- Is a 微信公众号 draft-creation integration worth adding later, given it is reachable and only draft-capable? Deferred deliberately.
